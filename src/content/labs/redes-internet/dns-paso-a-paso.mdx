Antes de que tu navegador hable con un servidor, tiene que resolver una duda básica: **¿a qué IP me conecto?** Esa respuesta para `example.com` la obtiene mediante DNS y puede cambiar con el tiempo. Entender la cadena de consultas explica muchos "en mi máquina anda".

<Callout type="concepto">
  **DNS** (Domain Name System) traduce nombres a direcciones IP. Vos preguntás
  un nombre; el sistema responde una IP. En el medio hay varios servidores que
  se pasan la pregunta hasta dar con el que tiene la respuesta autoritativa.
</Callout>

## La cadena, en un dibujo

<Mermaid
  caption="Una resolución típica: tu resolver pregunta hacia abajo hasta el servidor autoritativo."
  code={`flowchart TD
  A[Tu máquina] -->|example.com?| B[Resolver / recursivo]
  B -->|.com?| C[Root server]
  C -->|andá al TLD .com| B
  B -->|example.com?| D[Servidor TLD .com]
  D -->|andá al autoritativo| B
  B -->|example.com?| E[Servidor autoritativo]
  E -->|IP actual| B
  B -->|IP actual| A`}
/>

El **resolver** (normalmente el de tu ISP o uno como `1.1.1.1`) hace el trabajo sucio: pregunta al **root**, después al servidor del **TLD** (`.com`, `.ar`…), y por último al **autoritativo** del dominio, que tiene la respuesta real. Cada nivel solo sabe a quién derivarte.

## Verlo con dig

La respuesta corta, para confirmar a qué IP resuelve:

<TerminalBlock title="vt@labs:~">

```bash
dig +short example.com
```

</TerminalBlock>

Y la cadena completa, salto por salto:

<TerminalBlock title="vt@labs:~">

```bash
# +trace realiza la resolución iterativa directamente desde los root servers
dig +trace example.com
```

</TerminalBlock>

En una respuesta normal de `dig` mirás `ANSWER` (la respuesta), `AUTHORITY` (datos de autoridad, si aparecen) y el **TTL**, la segunda columna de cada registro. Esta salida es ilustrativa; consultá el valor actual con el comando anterior:

```text
;; ANSWER SECTION:
example.com.        3600    IN    A    <IPv4 observada>
;;                  ^TTL          ^tipo  ^valor
```

<Callout type="comando">
  El **TTL** (3600 = una hora) indica cuánto tiempo puede conservar un resolver
  esa respuesta desde que la recibió. Influye en cuándo volverá a consultar,
  pero no predice por sí solo cuándo todos verán un cambio. Para una migración,
  bajalo con anticipación: cambiarlo ahora no acorta el TTL de respuestas que
  otros resolvers ya guardaron.
</Callout>

## Los registros que más vas a ver

Estos ejemplos son esquemáticos, no una consulta actual a `example.com`:

```text
A       nombre → IPv4             example.com → <IPv4 actual>
AAAA    nombre → IPv6             example.com → <IPv6 actual>
CNAME   alias → otro nombre       www → example.com
MX      a dónde va el mail        example.com → mail.example.com
NS      quién es autoritativo     example.com → ns1.example.com
TXT     texto (SPF, verificación) "v=spf1 include:..."
```

<TerminalBlock title="vt@labs:~">

```bash
# Pedir un tipo puntual
dig example.com MX +short
dig example.com NS +short
```

</TerminalBlock>

<Callout type="error">
  El "funciona en mi máquina" clásico de DNS: vos ya tenés la **respuesta vieja
  cacheada** (en el SO, en el navegador o en tu resolver) y el otro no. No es
  magia ni mala suerte: puede ser el TTL de una respuesta vieja. `dig` no usa
  la caché interna del navegador; consulta al resolver configurado, que también
  puede tener su propia caché. Compará su respuesta con la de un servidor
  autoritativo antes de atribuir el problema al TTL.
</Callout>

## El criterio

Cuando un dominio "no anda", DNS es la primera parada:

```text
1. dig +short nombre      → ¿resuelve a algo? ¿a la IP correcta?
2. dig +trace nombre      → ¿en qué salto se rompe la cadena?
3. miro el TTL            → ¿un cambio reciente todavía está cacheado?
4. comparo resolvers      → dig @1.1.1.1 nombre vs el de mi ISP
```

<Callout type="concepto">
  Un fallo de DNS también puede deberse a delegación, conectividad, tiempos de
  respuesta o un registro incorrecto. `dig +trace` ayuda a revisar la cadena;
  comparar resolvers y el servidor autoritativo ayuda a distinguir caché de
  configuración. El TTL es una pista, no un diagnóstico completo.
</Callout>

## Evidencia esperada

Para completar este lab y registrar tu aprendizaje técnico, guardá tu writeup con este formato:

```text
[1] Saltos observados con dig +trace (ejemplo sintetizado):
- Salto 1: . (Root Servers)           → deriva a los servidores de .com (a.gtld-servers.net)
- Salto 2: .com (TLD Servers)         → deriva a los autoritativos del dominio (a.iana-servers.net)
- Salto 3: example.com (Autoritativo) → devuelve el registro A vigente

[2] Tabla de registros clave consultados:
- A:     IPv4 del host final
- AAAA:  IPv6 del host final
- MX:    Servidor de intercambio de correo y prioridad
- NS:    Servidor autoritativo delegado para la zona

[3] Writeup de propagación y caché:
Un resolver que guardó la respuesta anterior puede seguir entregándola hasta
que venza el TTL con el que la recibió. El TTL que consulto ahora no revela
cuánto le queda a cada caché ni garantiza un tiempo global de actualización.
```

<Callout type="evidencia">
  En operaciones, el trace muestra la cadena de delegación y ayuda a localizar
  dónde difieren las respuestas. Por sí solo no demuestra integridad ni descarta
  un desvío de tráfico.
</Callout>
